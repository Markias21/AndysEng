- 2026-08-07 | **GitHub Contents API 동기화 → Supabase(Postgres, 무료 등급) 전환.** 위 "친구 그룹 공유 지원"(2026-07-17, `shared/github.js`로 로그 프라이빗 레포에 push/pull) ADR을 **대체**한다. 계기는 이전에 별도 세션이 마이그레이션 코드(`shared/supabase.js`, `supabase/schema.sql`)를 작성해 뒀지만 커밋되지 않은 채 방치돼 있었던 것 — 병합 전 점검에서 두 번째 기기 로그인 불가·CSP 회귀(BBC·VOA 미디어 재생 재차단)·오프라인 실행 불가 등 여러 결함을 발견해 고치고 병합했다. **가입·로그인 화면(게이트) 설계는 이번 범위에서 제외** — 유저가 직접 다듬기로 해, 기존 2-모드 게이트(setup/unlock)를 최소한으로 Supabase Auth(`signUp`/`signIn`, 닉네임을 `<slug>@andyseng.internal` 가짜 이메일로 변환)에 연결하는 선까지만 했다(멀티유저 로그인·오프라인 분리·초대 코드 가입 제한 등은 후속 작업). 이번에 실제로 바꾼 것:
  1. **동기화 자체.** `andyseng_data` 테이블(user_id 1행, RLS로 본인 행만 select/insert/update)에 학습 기록을 저장. `saveRecord()`는 마지막으로 안 원격 `updated_at`이 있으면 그 값으로 조건부 PATCH(0행이면 "다른 기기에서 저장했어요" 충돌 안내), 없으면 insert — GitHub 시절의 `sha` 충돌 감지와 같은 역할을 낙관적 잠금으로 재현했다.
  2. **공용 콘텐츠 캐시로 2026-08-02 "레포 자동 커밋해 공유" 기각 ADR을 부분 재개.** 당시 기각 사유는 GitHub Contents API가 경로 단위 권한을 못 줘서 공유 PAT가 앱 소스 레포 전체(`index.html`·CSP 등)에 쓰기 권한을 갖게 되는 것이었다. Supabase RLS는 **테이블 단위**로 권한을 나눌 수 있어 그 문제가 없다 — `shared_sets(kind, key, payload, created_by)` 테이블을 새로 두고 select는 완전 공개(`anon`도 가능), insert는 로그인한 유저만, **update/delete 정책은 아예 두지 않아**(스키마 자체가 강제) 한 번 채워진 값을 아무도 못 고친다(첫 생성자 승). 리딩 문제 세트(`ai.js readySet`이 유저 캐시→레포 기본 세트→**공용 캐시** 순으로 확인)·6min 문제 세트(`sixmin/ai.js`, `readySet`을 동기에서 async로 변경)·사전 조회(`dictionary/ui.js lookup`)가 생성 직후 `putShared()`로 업로드해, 다음 유저부터는 이 셋 모두 AI 호출이 $0이 된다. 실패는 조용히 `null`/무시로 떨어져 오프라인·서버 오류에서도 기존 개인 캐시 폴백을 깨지 않는다.
  3. **동기화 페이로드 다이어트.** `store.syncPayload()`(순수 함수 `withoutSharedCaches`+테스트)가 `readingSets`·`sixMinSets`·`dict`를 뺀 나머지만 Supabase에 올린다 — 이 셋은 이제 공용 캐시에 있어 개인 페이로드에 중복 저장할 이유가 없다(리딩 세트만 지문당 최대 ~5KB, 유저 수만큼 곱해지던 것을 없앰). `exportJSON()`(로컬 리포트 백업용)은 그대로 전체를 담는다. 곁들여 `reading/ai.js readySet`이 레포 기본 세트를 찾았을 때 유저의 `store.readingSets`에 복사해 두던 동작도 없앴다(same-origin 파일은 서비스워커가 이미 캐시하므로 localStorage에 중복할 이유가 없다).
  4. **자동저장 범위 확장.** 기존엔 글쓰기 첨삭·회화 주제 전환·리딩 제출 3곳에서만 즉시 자동저장했고 가장 자주 쓰이는 복습(SRS)에는 아예 없었다. `shared/autosave.js`에 5초 디바운스 `scheduleSave()`(화면을 벗어나면 `visibilitychange`로 즉시 플러시)를 추가해 복습 채점·3분 학습(듣기·문단연습)·글쓰기 기본·리스닝(받아쓰기·이해문제) 기록 직후에도 자동저장이 걸리게 했다.
  5. **무료 등급 7일 무활동 일시정지 방지.** 이미 매일 도는 `.github/workflows/voa.yml`에 `curl` 한 스텝을 추가해 `shared_sets`를 조회한다(anon 키는 클라이언트 번들에 이미 공개된 publishable 키라 시크릿 불필요).

- 2026-08-16 | **관리자 승인제 가입 도입 — 위 "가입·로그인 화면 설계는 범위 밖" 결정을 해소.** 가입은 신청까지만 되고, 관리자(닉네임 `andy`)가 앱 안에서 승인해야 로그인이 열린다. 서버가 없어(anon 키만 브라우저가 쥔다) **강제는 전부 Postgres RLS가 하고, 화면 게이트는 UX일 뿐**이다. `supabase/002_approval.sql`(신규 마이그레이션, `schema.sql`은 그대로 두고 이어서 실행)에 `public.profiles(user_id, nickname, note, status pending|approved|rejected, is_admin, created_at, reviewed_at)`를 추가했다. `profiles`의 정책이 `profiles`를 다시 읽으면 재귀 에러가 나므로 `is_approved()`/`is_admin()`을 `security definer`로 둬 소유자 권한(RLS 우회)으로 재귀를 끊었다(`force row level security`는 이 우회를 깨서 절대 켜지 않는다). INSERT 정책은 신청자가 `status='pending'`·`is_admin=false`로만, **닉네임은 계정 이메일 로컬파트와 일치**해야만 통과시켜 남의 닉네임을 사칭해 관리자를 속이는 걸 막는다. UPDATE(심사)는 관리자만 가능하고, `with check`에 "자기 자신을 강등/거절할 수 없다" 조건을 넣어 관리자가 실수로 유일한 관리자 권한을 스스로 잠가버리는 사고를 막았다. 기존 `andyseng_data`/`shared_sets` 정책은 건드리지 않고 **`AS RESTRICTIVE`** 정책만 추가했다 — PERMISSIVE 정책끼리는 OR로 합쳐지므로 그냥 추가하면 조여지기는커녕 넓어지고, RESTRICTIVE라야 AND로 묶여 실제로 조여지며 롤백도 `drop policy` 한 줄로 끝난다(`shared_sets`는 로그인 전 anon 공개 읽기가 있어 `for insert`에만 건다). 클라이언트: `shared/supabase.js`에 `signUpRequest`(가입+profiles insert, 끝나면 세션을 지워 승인 전엔 로그인으로만 들어오게 함)·`fetchProfile`/`ensureProfile`(신청이 네트워크 중간에 끊겨 관리자 목록에 안 보이는 경우 복구)·`listProfiles`/`reviewProfile`(관리자용, PATCH가 RLS에 막히면 200+0행으로 오므로 반환 행 수를 확인해 거짓 성공을 막는다) 추가. `app.js`의 `showGate`가 `setup`(신청)·`unlock`(로그인)·`pending`(승인 대기, 신규) 3모드를 다루고, 로그인 성공 뒤 `enterIfApproved`가 승인 상태를 확인해 `approved`가 아니면 세션을 지우고 도로 `pending` 화면으로 돌려보낸다. 최초 1회 로컬 기록 업로드는 가입 시점에서 **최초로 승인된 로그인 시점**으로 옮겼다(가입 직후엔 RLS가 `andyseng_data` 쓰기를 막으므로). 관리자 화면은 새 기능 폴더 `features/admin/`(`requests.js` 순수 정렬 함수+테스트, `ui.js`)로 분리해 설정 모달 안에 `#admin-panel`로 붙였다 — pending·approved·rejected 전체를 한 목록에 보여줘 거절도 나중에 승인으로 되돌릴 수 있게 했다. 부트스트랩(최초 관리자 지정)은 SQL 백필로 하지 않는다 — 마이그레이션 적용 시점에 실제 가입 계정이 아직 없었기 때문에, 대신 **가입 신청 → `scripts/db.js`(service_role, RLS 우회)로 그 프로필 행에 `status='approved', is_admin=true`를 직접 써서 자기 자신을 최초 관리자로 승격**하는 순서를 쓴다(관리자가 없으면 아무도 승인 UPDATE 정책을 통과 못 하는 닭-달걀 문제의 해법). 검증: `chrome-headless-shell`을 CDP로 직접 몰아 새 DOM 요소(메모 입력·승인 대기 화면·관리자 패널)와 폼 전환·에러 처리(마이그레이션 미적용 상태에서 가입이 실패해도 로컬 금고를 만들지 않고 안전하게 멈추는지)를 확인했고, 그 과정에서 생성된 테스트 계정은 Auth admin API로 정리했다. `sw.js` `VERSION` v18→v19 + 새 파일 프리캐시 목록 추가 | 유저가 가입 신청→관리자 승인 흐름을 요청. 서버 없는 정적 PWA에서 승인을 강제할 유일한 방법은 RLS이고, 화면 게이트는 그 위에 얹힌 UX일 뿐이라는 점을 명시해 둔다.
